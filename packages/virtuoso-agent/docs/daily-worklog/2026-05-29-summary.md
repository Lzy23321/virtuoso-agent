# 2026-05-29 工作总结：virtuoso-agent 当前结构、运行逻辑与下一阶段计划

本文用于给后续新窗口快速接续上下文，也用于帮助人类开发者理解当前 `packages/virtuoso-agent` 的代码组织和运行流程。

## 当前定位

`virtuoso-agent` 不是新的 agent runtime。它是一个 Virtuoso 自动化能力包，当前遵守三层分离：

```text
src/runtime
  可迁移的 Virtuoso 自动化核心逻辑

src/extension
  pi agent 专用 adapter，把 runtime 能力注册成 pi tools

src/cli
  命令行 adapter，给 shell、Codex、Claude Code 等调用
```

pi agent 负责对话、LLM、tool calling、session、UI。`virtuoso-agent` 负责 task schema、job artifacts、Spectre/OCEAN/SKILL backend、结果解析和 proposal 输出。

### CLI 层

```text
src/cli/main.ts
```

很薄的进程入口。只负责：

```text

```

```text
src/cli/runner.ts
```

真正的 CLI adapter。负责：

- 判断命令类型
- 调用 runtime
- 输出 JSON
- 返回 exit code

当前支持：

```bash
vab status --json

```

重要：`runner.ts` 不实现 Virtuoso 业务逻辑，只把 CLI 参数转换为 runtime 调用。

### pi extension 层

```text
src/extension/index.ts
```

pi agent adapter。注册三个工具：

- `virtuoso_status`
- `virtuoso_task_validate`
- `virtuoso_run_task`

大模型不会直接运行代码。模型只会决定调用工具，真正执行的是 pi 的 Node.js 进程：

```text
LLM tool call
-> pi runtime 执行 tool.execute()
-> tool.execute() 调用 src/runtime
-> 结果返回给 LLM
```

### runtime core

```text
src/runtime/core/result.ts
```

统一 runtime 返回格式：

```ts
RuntimeResult<T> =
  | { ok: true; value: T }
  | { ok: false; error: RuntimeError }
```

所有 workflow/backend 尽量返回结构化错误，而不是直接抛异常。

```text
src/runtime/core/task-schema.ts
```

task 输入合同。负责校验 JSON task。

当前支持 backend：

```text
fake
spectre
ocean
ocean-xl
```

当前规则：

- `spectre` 必须有 `simulation.netlist`
- `ocean` / `ocean-xl` 必须有 `simulation.script`
- `parameters`、`outputs`、`safety`、`simulation.spectre` 都有基础类型校验
- `simulation.spectre` 支持 `format`、`mode64`、`preset`、`lqtimeout`、`maxWarnings`、`maxNotices`、`env`、`ahdlLibDir`、`additionalArgs` 等选项

```text
src/runtime/core/job.ts
```

job artifacts scaffold。负责创建 job 目录、复制 task、提供标准产物路径、写 JSON/text artifact。

标准 artifact：

```text
task.json
input.scs
psf/
psf/spectre.out
stdout.log
stderr.log
metrics.json
proposal.json
result.json
```

默认 job root：

```text
<task-dir>/.virtuoso-agent/jobs/<job-id>/
```

CLI 可通过 `--jobs-root` 指定其它目录。

```text
src/runtime/core/process-runner.ts
```

通用外部进程执行器，不包含 Spectre 知识。

能力：

- 构造结构化 `ProcessRunResult`
- 支持 `dryRun`
- 支持注入 fake executor
- 捕获 executor 异常并转成 `process_run_error`

### runtime backend

```text
src/runtime/backends/spectre/runner.ts
```

Spectre backend 的命令构造与执行。

当前构造命令形态：

```bash
spectre -64 input.scs \
  +escchars +log psf/spectre.out \
  -format psfbin -raw psf \
  +preset=mx +mt +lqtimeout 900 \
  -maxw 5 -maxn 5 -env ade \
  +logstatus
```

支持覆盖：

- `spectreBin`
- `format`
- `preset`
- `lqtimeout`
- `maxWarnings`
- `maxNotices`
- `env`
- `ahdlLibDir`
- `additionalArgs`
- `dryRun`
- fake executor

非 0 exit code 返回 `spectre_process_error`。

### runtime workflow

```text
src/runtime/workflows/status.ts
```

当前返回 scaffold 状态：

```text
mode: scaffold
bridgeConnected: false
```

后续可以扩展为检查 Spectre/OCEAN/Virtuoso bridge 状态。

```text
src/runtime/workflows/run-task.ts
```

当前最重要的 workflow。

运行流程：

```text
runTask(taskPath, options)
-> validateTaskFile(taskPath)
-> createJob()
-> 根据 task.simulation.backend 分发
   -> fake
   -> spectre
   -> ocean/ocean-xl: backend_not_implemented
-> 写 stdout.log / stderr.log
-> 写 metrics.json / proposal.json
-> 写 result.json
-> 返回 RuntimeResult<RunTaskResult>
```

Spectre 分支流程：

```text
原始 netlist path
-> copy 到 job/input.scs
-> 扫描原始 netlist 里的相对 include
-> 对相对 include root 建 symlink 到 job 目录
   例如 job/pdk -> 原始目录/pdk
-> 在 job 目录下执行 spectre input.scs
-> raw 结果写 job/psf
-> log 写 job/psf/spectre.out
```

这个策略的目的：

- 不修改用户原始网表
- 每次运行都有可复现快照
- agent 出错后可审计
- 支持相对 include，同时避免复制整个 PDK

## 从用户角度看，后续产品流程应是什么

用户打开一个能使用 Virtuoso 的聊天框，第一步通常不是直接给 netlist 路径，而是想知道：

```text
当前环境有哪些 library？
每个 library 有哪些 cell？
每个 cell 有哪些 view？
哪些是 schematic / symbol / layout / veriloga / maestro？
哪个 testbench 可以仿真？
```

因此下一阶段应优先补 **Design Library Discovery**，让模型通过工具稳定了解当前电路环境，而不是靠大模型猜文件系统。

## 下一阶段计划

### 1. 先做设计库发现能力

新增建议：

```text
src/runtime/design-libs/types.ts
src/runtime/design-libs/cds-lib.ts
src/runtime/design-libs/discover.ts
test/runtime/design-libs/discover.test.ts
```

第一版从文件系统和 `cds.lib` 入手，不依赖 Virtuoso GUI。

目标 API：

```ts
discoverDesignLibraries({
  cdsLibPath: "/path/to/cds.lib"
})
```

返回结构：

```ts
{
  libraries: [
    {
      name: "test_tb",
      path: "...",
      cells: [
        {
          name: "two_stage_amp_tb",
          views: ["schematic", "symbol", "maestro"]
        }
      ]
    }
  ]
}
```

后续 CLI：

```bash
vab design list --cds-lib <path> --json
```

后续 pi tool：

```text
virtuoso_design_list
```

这样用户问“当前有哪些电路”时，模型调用工具，工具返回稳定 JSON，模型只负责总结。

### 2. 整理 Spectre prepare 逻辑

当前 `run-task.ts` 已经开始变大，里面包含 Spectre 细节：

- copy netlist
- scan include
- symlink include root
- Spectre 默认参数

建议拆到：

```text
src/runtime/backends/spectre/prepare.ts
src/runtime/backends/spectre/options.ts
```

目标：

```text
run-task.ts
  只负责 workflow 编排

spectre/prepare.ts
  负责 input.scs、relative include、job workspace

spectre/runner.ts
  负责命令构造和 process runner
```

### 3. 补 Spectre log parser

新增：

```text
src/runtime/parsers/spectre-log.ts
test/runtime/parsers/spectre-log.test.ts
```

第一版解析：

```ts
{
  completed: boolean;
  errors: number;
  warnings: number;
  notices: number;
  elapsedSeconds?: number;
  peakMemoryMb?: number;
  analyses: string[];
}
```

这会让 agent 不只知道 process exit code，还能知道仿真是否完成、warning 数、analysis 列表。

### 4. 补 metrics extraction 第一版

从 `spectre.out` 文本先解析明显指标。

例如当前成功 log 里有：

```text
Phase margin = 48.9529 Deg at frequency = 49.627 MHz
```

可先输出：

```json
{
  "phaseMarginDeg": 48.9529,
  "phaseMarginFreqHz": 49627000
}
```

后续再考虑 PSF parser 或 Ocean 读取。

### 5. 改善 pi tool 文本摘要

`src/extension/index.ts` 目前只返回很简单的文本。后续应基于 runtime 的结构化结果返回摘要：

```text
Spectre simulation finished.
Job: ...
PSF: ...
Log: ...
Warnings: ...
Metrics: ...
```

注意：extension 只做 adapter，不在 extension 里解析 log。

### 6. 处理 build/type 问题

当前 package build 曾失败在：

- `@earendil-works/pi-ai` / `@earendil-works/pi-coding-agent` dist 类型解析
- `src/extension/index.ts` 隐式 any

后续需要：

- 确认 monorepo 依赖 package 是否已 build

- 重新验证 `npm run build -w @lzy23321/virtuoso-agent`

### 7. 后续再考虑 Virtuoso SKILL bridge

暂时不急着接 GUI/SKILL bridge。合理路线：

```text
Design library discovery
-> 用户选择 lib/cell/view/testbench
-> netlist/task 生成或定位
-> Spectre run
-> log/metrics parser
-> proposal
-> 再接 SKILL bridge 做 schematic 参数修改
```

SKILL bridge 未来职责：

```text
VirtuosoClient
  连接 Virtuoso bridge daemon
  发送受控 SKILL
  返回结构化结果
```

不要让大模型临场自由生成大段 SKILL。应该提供人类工程师设计过的高层工具，例如：

```text
schematic.list_libraries
schematic.list_cells
schematic.open_cellview
schematic.update_parameter
schematic.save
schematic.check
```
